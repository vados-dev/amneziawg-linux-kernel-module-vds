# Отчёт 13.11.2026 16:15 MSK — единый контракт уведомлений

Основание: лог `.agents/logs/debug/131120261554-check-upstream.yml.log`,
запись в `06-debug.md` (13.11.2026 16:15), план Phase D в `04-plans.md`.

## 1. Что было не так

Прогон `131120261554` при `in_sync=false` (upstream `v3.1.20261113-02`, база `v3.1.20260812`)
отправил два Telegram-сообщения об одном событии:

| Время (UTC) | Шаг | Текст | Строки лога |
|---|---|---|---|
| 12:52:30 | Notify Telegram about upstream update | «Upstream v3.1.20261113-02 released. merge.yml was not started (NOTIFY_ON_UPDATE=true)» | 213–232 |
| 12:52:34 | Notify Telegram on result | «check-upstream: success» | 233–253 |

Оба флага разрешились в `true` (лог `:53-54`). Источник значения (dispatch или repo variable)
из лога неразличим, потому что имя инпута и имя env совпадали.

Дефекты:

1. `NOTIFY_ON_UPDATE` управлял запретом автозапуска `merge.yml`, а не уведомлением.
   В `merge.yml` тот же флаг означал другое, в `stable.yml` не использовался вовсе.
2. Два независимых флага описывали одну ось — конфликт не валидировался.
3. `inputs.X || vars.X == 'true'` не позволял выключить флаг из dispatch:
   boolean всегда определён, `false` означал «взять из vars».
4. Одна сущность жила в трёх типах: boolean-инпут → выражение → строковый env.
5. `-F NOTIFY_ON_UPDATE` при запуске merge выполнялся только при `!= 'true'`,
   то есть всегда передавал `false`.
6. `always()` в шаге результата отправлял «success» и при `in_sync=true`.
7. При `auto_merge=true` владелец получил бы 2–3 сообщения по одной цепочке.

## 2. Что изменено

### `.github/workflows/check-upstream.yml`

- `workflow_dispatch.inputs`: удалены `NOTIFY_ON_UPDATE` и `NOTIFY_ON_RESULT`;
  добавлены `auto_merge` (boolean, default `false`) и `notify_mode`
  (`type: choice`, `options: [none, inherit, changes, always]`, default `none`).
- `env`: `TELEGRAM_ENABLED` (kill-switch `vars.TELEGRAM_NOTIFY`), `NOTIFY_MODE_INPUT`,
  `NOTIFY_MODE_VAR`, `AUTO_MERGE`, `DRY_RUN`.
- Новый шаг `Resolve notification mode` (`id: notify`): `changes`/`always` из инпута
  переопределяют env; `none`/`inherit` берут `vars.NOTIFY_MODE`, при пустом значении —
  `changes`; при `TELEGRAM_NOTIFY=false` режим принудительно `none`.
  Результат пишется в `GITHUB_ENV` (`NOTIFY_MODE`) и в outputs.
- Шаг `Start merge workflow` теперь зависит только от `inputs.auto_merge`,
  передаёт `-f notify_mode="$NOTIFY_MODE"` и `-F dry_run="$DRY_RUN"`.
- Три шага Telegram сведены в один `Notify Telegram`:
  `always() && TELEGRAM_ENABLED && NOTIFY_MODE != 'none'`. Текст собирается по фактическому
  исходу (сбой / in-sync / новый тег), при `changes` и `in_sync=true` сообщение не отправляется.

### `.github/workflows/merge.yml`

- В `workflow_call` — `notify_mode` (`type: string`, default `"none"`),
  в `workflow_dispatch` — `type: choice` с теми же опциями.
- `NOTIFY_ON_UPDATE`/`NOTIFY_ON_RESULT` удалены; `env` переведён на `TELEGRAM_ENABLED`,
  `NOTIFY_MODE_INPUT`, `NOTIFY_MODE_VAR`.
- Добавлен шаг `Resolve notification mode` (`id: notify`) первым в job `merge`;
  значение опубликовано в `outputs.notify_mode`.
- Уведомление о корневых файлах upstream (правило 11) выполняется только при
  `TELEGRAM_ENABLED` и `NOTIFY_MODE != 'none'`.

## 4. Действия владельца

1. Repository variables:
   - `NOTIFY_MODE` — режим по умолчанию: `changes` или `always` (не задана → `changes`);
   - `TELEGRAM_NOTIFY` — `true`/`false`, глобальный выключатель (не задана → включено);
   - `DEFAULT_TAG` — без изменений.
2. Проверить прогоны (правило 7 — запускает владелец):
   - `notify_mode=none` → сообщений нет;
   - `notify_mode=changes` при `in_sync=true` → сообщений нет;
   - `notify_mode=changes` при новом теге → ровно одно сообщение;
   - `notify_mode=always` → ровно одно сообщение на любой исход;
   - `auto_merge=true` + `dry_run=true` → merge запускается, `notify_mode` доходит до merge
     и stable.
3. Проверить, что `gh workflow run merge.yml -f notify_mode=...` принимает значение
   из списка опций.
